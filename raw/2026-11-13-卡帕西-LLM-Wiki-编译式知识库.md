# 卡帕西 LLM Wiki：AI 驱动的编译式知识库

> 整理说明：本文将本对话的讨论与上方所列的原始 idea file 整理为中文资料。关于该模式的定义、架构与操作流程，以该 idea file 为准；本文的“当前仓库映射”是针对本知识库的实现说明，不是卡帕西原文。

## 核心想法

卡帕西提出的 LLM Wiki 是一种用 LLM 构建个人知识库的模式。与“提问时才从原始文档中检索片段并临时生成答案”的常见 RAG 工作流不同，LLM 会在每次加入新资料时，增量维护一套持久化、互相链接的 Markdown Wiki。

新资料不会只被索引：LLM 会阅读资料，抽取关键信息，更新实体页和主题总结，记录新旧资料之间的矛盾，并调整已有综合结论。知识在摄取时被“编译”，随后持续维护，而不是在每次查询时从头拼接。

该模式将 Wiki 视为会随着资料和问题不断丰富的复利型产物。人主要负责选择资料、探索问题并指导重点；LLM 负责摘要、交叉引用、归档和维护。

## 三层架构

1. **原始资料（raw sources）**：文章、论文、图片、数据文件等经筛选的资料集合。它们不可变，是可追溯的事实来源。
2. **Wiki**：由 LLM 生成和维护的 Markdown 页面，包括来源摘要、实体页、概念页、比较、概览和综合内容。
3. **Schema**：如 `AGENTS.md` 或 `CLAUDE.md` 的规则文档，用于规定目录结构、内容约定及摄取、查询和维护流程。

## 三项核心操作

### 摄取（Ingest）

用户将新资料放入原始资料集合并要求 LLM 处理。LLM 阅读资料、讨论重点、创建来源摘要、更新索引和关联页面，并向日志追加记录。原始说明指出，一份资料可能影响 10–15 个页面；也可以逐篇、在人类参与下摄取。

### 查询（Query）

用户针对 Wiki 提问。LLM 先定位相关页面，阅读后综合并附上引用。值得长期保留的比较、分析或发现可以再写回 Wiki，使对话成果不只停留在聊天记录中。

### 巡检（Lint）

定期让 LLM 检查页面矛盾、被新资料淘汰的陈述、孤立页面、缺失概念页、缺少交叉链接和可由新资料补足的信息缺口。

## 索引与日志

`index.md` 是面向内容的目录：列出 Wiki 页面及其简要说明，供人和 LLM 在查询时定位相关内容。`log.md` 是按时间追加的操作记录：保存资料摄取、查询和巡检的历史。

原始说明认为，在约百份资料、数百个页面的中等规模下，维护良好的索引可先承担导航作用，未必立即需要基于嵌入的 RAG 基础设施；随着规模增长，可以再增加本地全文或混合检索工具。

## 与 RAG 的关系

RAG 的重点是查询时从原始资料检索相关片段；LLM Wiki 的重点是摄取时将资料提炼为可维护的页面和链接。两者并不互斥：Wiki 可使用搜索或 RAG 辅助定位页面，RAG 系统也可预先维护结构化的知识页面。

## 当前仓库映射（整理者说明）

本仓库以 `raw/` 保存不可变资料，以 `wiki/` 保存 Agent 维护的知识页面，以 `output/` 保存一次性产物，以 `assets/` 保存附件和图片，并以 `AGENTS.md` 作为 schema。这是对上述模式的一种具体实现。

## 边界与注意事项

- 原始 idea file 是一个抽象模式说明，不是固定的软件实现；目录结构、页面格式和工具可按领域调整。
- Wiki 是 LLM 生成的二级产物。重要事实需保留到原始资料的可追溯链接，不能只依赖摘要。
- LLM 的维护并不自动保证正确；冲突、不确定性和待核验项应显式保留。
- 是否采用向量检索、全文搜索、图片处理或演示文稿等能力，应随资料规模和实际需求逐步增加。
